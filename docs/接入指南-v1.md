# enter-harness 宿主接入指南 v1

> 适用对象：把 `enter_harness` 当运行时依赖、需要装配 10 个治理端口的产品宿主。
> 核对基准：2026-10-23，`enter_harness/harness/*`、`enter_harness/context/{ports,store,pipeline}.py`、`tests/test_harness_ports.py`。
> 本文只写当前代码可验证的行为；哪些端口已接入 `Agent`、哪些仍是宿主自行编排，见 §7。

## 0. 术语

| 术语 | 中文解释 |
|---|---|
| 内核 | 模型之外的运行时治理层：管输入、上下文、动作、状态、验收、审计 |
| Port（端口） | 只定方法契约、不定存储与厂商的接口；宿主无需继承 |
| Wiring（装配） | 启动时把 10 个端口实例装进 `PortSet` 并做一次完整性检查 |
| Checkpointer（检查点存储） | 保存图执行中间状态的组件；LangGraph 自带实现 |
| Replay（重放） | 从检查点恢复并继续执行 |
| Hash chain（哈希链） | 每条审计记录带前一条的哈希，改任一条都会导致校验失败 |

## 1. 宿主启动时装配 10 端口

### 1.1 总表

`PortSet` 的 10 个字段默认全是 `None`，**不会自动实例化任何默认实现**。宿主即使想用默认实现，也必须显式 `new` 出来传进去。

| 端口名 | 默认实现 | 宿主必须提供什么 | 不提供会怎样 |
|---|---|---|---|
| `identity`（`IdentityPort`） | `StaticIdentityPort`（本地/测试） | 产品账号/认证系统的适配器，实现 `resolve(req=None) -> dict`，至少含 `tenant_id` / `user_id` / `roles`；只读，不得从对话推断 | `PortSet.invalid()` 列出 `identity`；`check()` 抛 `TypeError`，启动失败 |
| `context`（`ContextPort`） | 无 | 产品块存储，实现 `list_blocks(scope="", scope_id="") -> BlockMeta[]` 与 `get_block(block_id, version=0) -> Block \| None`；`list_blocks` 只回元数据 | 同上，启动失败 |
| `memory`（`MemoryPort`） | `StoreMemoryPort` / `MarkdownMemoryPort` / `PostgresMemoryPort` | 传入存储实例或自研实现，方法为 `query(req)` / `upsert(item)` / `archive(ids)`；查询请求必须带 `tenant_id`、`scope`，按智能体隔离时还要带 `agent_id` | 同上；若把 `SQLiteMemoryStore` 直接当端口传入，`query` 签名不符，运行期出错（见 §8） |
| `knowledge`（`KnowledgePort`） | 无 | 知识库/向量库适配器，必须同时实现 `search(query, top_k=4, scope="")` 和 `get_chunk(chunk_id)`；命中必须带 `source` | 缺 `get_chunk` 也判为不完整，启动失败 |
| `policy`（`AccessPolicyPort`） | 无 | 产品权限系统（RBAC/ABAC），实现 `can(identity, action, target) -> bool`；异常按拒绝处理 | 启动失败 |
| `ingest`（`IngestPort`） | `DefaultIngestPort` | 只需实例化并传入；运行期把用户输入、工具结果、事件、附件指针交给 `collect(req)` | 启动失败（不会自动补默认实例） |
| `action`（`ActionPort`） | `ToolActionPort(registry)` | 必须传一个具备 `list_tools()` 与 `execute(name, args, ctx)` 的注册表（`ToolRegistry` 满足）；审批队列默认 `InMemoryApprovalQueue`，多副本部署应换 `SQLiteApprovalQueue` | 启动失败；只装配 `AccessPolicyPort` 不会自动给工具调用加策略，工具策略要另行注入注册表 |
| `state`（`StatePort`） | `SQLiteStatePort` / `PostgresStatePort` | 指定存储路径/DSN，或提供 LangGraph checkpointer 适配器；实现 `load` / `save` / `checkpoint` / `resume` / `list_checkpoints` | 启动失败 |
| `verify`（`VerifyPort`） | `RuleVerifyPort` | 可直接用；需要领域验收规则时替换实现，方法 `check(result, criteria=None, ctx=None) -> Verdict` | 启动失败 |
| `audit`（`AuditPort`） | `SQLiteAuditPort` / `PostgresAuditPort` | 指定存储路径/DSN 与留存天数；生产可换产品审计库/SIEM；方法 `emit(event)` / `query(filter)` | 启动失败；即使装配了，不把 `audit` 传给 `ToolActionPort` 也不会自动记录工具调用 |

### 1.2 本地存储四件套（三套后端）

```python
from enter_harness.harness import build_local_ports

ports = build_local_ports("/data/agent", backend="sqlite")      # 默认
ports = build_local_ports("/data/agent", backend="markdown")    # 人可读写
ports = build_local_ports("/data/agent", backend="postgres",    # 多副本/服务端
                          dsn="postgresql://user:pass@host:5432/db")
```

| 后端 | 记忆 / 知识 | 状态 / 审计 | 额外依赖 |
|---|---|---|---|
| `sqlite` | SQLite | SQLite | 无 |
| `markdown` | Markdown 文件 | 仍落 SQLite | 无 |
| `postgres` | PostgreSQL | PostgreSQL | `psycopg[binary]>=3.1` |

- PostgreSQL 安装：`pip install 'enter-harness[postgres]'`；
- DSN 可传参，也可用 `HARNESS_PG_DSN` / `DATABASE_URL` / `PG*` 环境变量；
- PG 端口构造时自动建 `harness_*` 表，**不需要**单独 migration；
- 每个端口一个连接 + 线程锁；连接池由宿主负责；退出前调用 `ports.close()`；
- 三套后端之间**没有**自动迁移命令。

完整步骤、权限、并发与排错见 `使用手册-v1.md` §3；
目录与表结构见 `本地存储格式-v1.md`。

### 1.3 三个装配事实

| 事实 | 说明 |
|---|---|
| `PortSet.check()` 会抛异常，不返回 `False` | 成功返回 `True`；失败抛 `TypeError("内核端口不完整：...")`，消息里带缺失名字 |
| `missing()` 与 `invalid()` 不同 | `missing()` 只看是否为 `None`；`invalid()` 还做 `isinstance(..., Protocol)` 检查，是 `check()` 的实际依据 |
| `isinstance` 检查只查方法名 | `runtime_checkable` 的协议检查不校验参数个数、参数名、返回类型；签名错的类也可能通过，见 §8 |

端口与一级模块的对应关系（`MODULE_PORTS`）：

| 一级模块 | 二级端口 |
|---|---|
| definition（定义层） | `identity` |
| observation（观测） | `ingest` |
| context（上下文） | `context` / `memory` / `knowledge` |
| control（控制） | `ModelPort`（基础端口，不计入 10 个） |
| action（动作） | `action` / `policy` |
| state（状态） | `state` |
| verification（验收） | `verify` / `audit` |

## 2. 最小 wiring 示例

以下代码可直接复制到宿主的启动模块。占位类的位置就是产品必须实现的部分。

```python
from pathlib import Path

from enter_harness.context import SQLiteMemoryStore
from enter_harness.harness import (
    DefaultIngestPort,
    PortSet,
    RuleVerifyPort,
    SQLiteApprovalQueue,
    SQLiteAuditPort,
    SQLiteStatePort,
    StoreMemoryPort,
    ToolActionPort,
)
from enter_harness.tools import ToolRegistry

DATA = Path("data")
DATA.mkdir(exist_ok=True)


# ---- 以下 4 个类必须由产品实现，这里只是可启动的占位 ----

class ProductIdentity:
    """身份事实来自账号/认证系统，不得从对话推断。"""
    def resolve(self, req=None):
        return {"tenant_id": "t1", "user_id": "u1", "roles": ["user"]}


class ProductContext:
    """块存储。list_blocks 只回元数据，正文由 get_block 按需读。"""
    def list_blocks(self, scope="", scope_id=""):
        return []

    def get_block(self, block_id, version=0):
        return None


class ProductKnowledge:
    """知识检索与按 id 回取；search 命中必须带 source。"""
    def search(self, query, top_k=4, scope=""):
        return []

    def get_chunk(self, chunk_id):
        return None


class ProductAccessPolicy:
    """演示用 AllowAll；生产必须接 RBAC/ABAC，异常按拒绝处理。"""
    def can(self, identity, action, target):
        return True


# ---- 工具与审计 ----

registry = ToolRegistry()
registry.register("echo", lambda text="": text, description="回显文本")

audit = SQLiteAuditPort(str(DATA / "harness-audit.db"))

ports = PortSet(
    identity=ProductIdentity(),
    context=ProductContext(),
    # 必须走 StoreMemoryPort：端口 query 收 req dict，存储 query 收列参数
    memory=StoreMemoryPort(SQLiteMemoryStore(str(DATA / "harness-memory.db"))),
    knowledge=ProductKnowledge(),
    policy=ProductAccessPolicy(),
    ingest=DefaultIngestPort(default_scope="project", default_scope_id="p1"),
    # 单进程可用默认 InMemoryApprovalQueue；多副本必须换持久队列
    action=ToolActionPort(
        registry,
        queue=SQLiteApprovalQueue(str(DATA / "harness-approval.db")),
        audit=audit,
    ),
    state=SQLiteStatePort(str(DATA / "harness-state.db")),
    verify=RuleVerifyPort(),
    audit=audit,
)

print(ports.missing())   # []
print(ports.invalid())   # []
assert ports.check() is True
```

预期输出：

```text
[]
[]
```

说明：

- 示例的端口装配部分已在仓库 Python 3.12.6 下用 `:memory:` 数据库等价执行，`missing=[]`、`invalid=[]`、`check=True`。
- `action` 的注册表既可以是 `enter_harness.tools.ToolRegistry`（`list_tools` 返回 dict），
  也可以是 `enter_harness.tooling.ToolRegistry`（返回 `FunctionTool`）；`ToolActionPort`
  内部统一成 dict，执行结果兼容 `ToolResult`，宿主不需要写翻译层。
- 同一任务里 `audit` 同时传给 `ToolActionPort` 和 `PortSet`，工具/审批事件会进入同一条哈希链。
- 工具级策略要传给 `ToolRegistry(policy=...)`；`AccessPolicyPort` 管的是数据/目标访问判定（`assemble` 里用于块的 `read` 判定），两者不是同一个对象。

## 3. 一次运行的调用顺序

```text
0 定义层 → 1 采集 → 2 选择/预算 → 3 拼装 → 4 请求
                                            │
                          5 动作/审批 → 6 状态 → 7 验收
                                            │
                          8 审计（横切 0~7） → 9 回流 → 下一轮 1/2
```

| 步 | 做什么 | 调用与方法 | 涉及端口 | 关键行为 / 失败语义 |
|---|---|---|---|---|
| 0 | 确定“谁在操作” | `resolve(req)` | `identity` | 返回带 `tenant_id` / `user_id` / `roles` 的字典；不能从对话推断 |
| 1 | 采集输入 | `collect(req)` → `RawInput[]` | `ingest` | 统一用户输入、工具结果、事件、文件引用；空正文项被丢弃；工具结果回采也走这里 |
| 2 | 选择候选 + 设预算 | `list_blocks(scope, scope_id)`；`query(req)`；`search(query, top_k, scope)` | `context` / `memory` / `knowledge` | 前两步由宿主编排；核心 `assemble` **不会**自动查记忆和知识，需把结果转成 `extra_blocks` 传入。`search` 命中无 `source` 的要丢弃 |
| 3 | 拼装上下文 | `assemble(context=..., identity=..., policy=..., scope=..., extra_blocks=..., max_total_chars=...)` | `context` / `policy`（内部调用） | `assemble` 内部依次 collect → authorize（`can(identity, "read", BlockMeta)`）→ rank → fetch（缓存未命中才 `get_block`）→ budget → compose；`procedural`（规范/规则）块超限直接抛 `ContextOverflow`，不截断 |
| 4 | 请求模型 | `complete(messages, tools, budget)` / `stream(...)` / `count_tokens(...)` / `embed(...)` | `ModelPort`（基础端口，不计入 10 个） | 模型可返回文本或工具调用；预算参数由宿主传入 |
| 5 | 动作 / 审批 | `list_tools(identity, scope)`；`call(identity, name, args, ctx)` → `ActionResult`；必要时 `request_approval` / `resume` | `action` / `policy` | `call` 内部异常会映射成 `status="error"` 的 `ActionResult`，不向上抛；工具注册表自身的 policy 与 `AccessPolicyPort` 是两套，需分别注入 |
| 6 | 状态持久化 | `save(thread_id, state)`；`checkpoint(thread_id, node, state)`；`resume(thread_id)`；`list_checkpoints(thread_id)` | `state` | 不要求每步都存；暂停审批前和关键节点后至少各存一次；只存运行状态，长期记忆走 `memory` |
| 7 | 验收 | `check(result, criteria=None, ctx=None)` → `Verdict` | `verify` | `RuleVerifyPort` 是确定性规则，不调模型；只判定，不执行修复；是否重试由控制层决定 |
| 8 | 审计 | `emit(AuditEvent)`；`query(filter)` | `audit` | 横切 0~7，不参与业务判断；`ToolActionPort` 在传入 `audit` 时会自动记录工具调用与审批事件 |
| 9 | 回流 / 存储 | `upsert(MemoryRecord)`；必要时 `archive(ids)` | `memory` | `StoreMemoryPort.upsert` 走统一写入契约，返回 `append` / `supersede` / `noop` / `invalid`；工具结果再交给第 1 步采集，进入下一轮选择 |

### 3.1 `assemble` 返回字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `text` | `str` | 保留下来的块正文，按 `"\n\n"` 连接 |
| `blocks` | `list[dict]` | 仅保留块，字段为 `id` / `kind` / `authority` / `scope` / `version` / `content_hash` |
| `trace` | `list[dict]` | 逐块诊断：缓存状态 `inline/hit/fetched`、字符数、丢弃原因、`error`、`hash_mismatch` 等 |
| `used_chars` | `int` | 实际占用字符数 |
| `dropped` | `list[str]` | 被丢弃块的 id（重复、空正文、超单块上限、超总预算、被鉴权拒绝） |
| `truncated` | `list[str]` | 当前实现固定为 `[]`：预算策略是整块丢弃，不输出半段 |

`trace` 中成功块也带 `"truncated": False`；不要把该字段理解为“发生过截断”。

### 3.2 选择阶段的边界

| 事项 | 当前代码行为 |
|---|---|
| 记忆选择 | `assemble` 不调用 `MemoryPort`；宿主先 `query`，再把结果转成 `Block` 放进 `extra_blocks` |
| 知识选择 | `assemble` 不调用 `KnowledgePort`；同上 |
| `extra_blocks` 可接受的类型 | 只接受 `Block` 或 `BlockMeta`；直接传 `MemoryRecord` 会抛 `TypeError` |
| 鉴权目标 | `policy.can(identity, "read", meta)` 传的是 `BlockMeta`，不是正文 `Block` |
| 异常处理 | `list_blocks` / `get_block` 抛异常会记入 `trace` 并继续，不拖垮整轮；策略异常按拒绝处理 |
| 块排序（D1） | `BlockMeta.sort_key` 使用 `scope_rank(kind, scope)`，与 `select_records` 一致：semantic 为 project → platform → user，procedural 为 platform → project → user，profile 为 user → project → platform |

### 3.3 工具可见性

`list_tools(identity, scope)` 会同时按身份与 scope 过滤：

- 工具可声明 `scope` / `tenants` / `roles`；
- 声明了限制但身份不满足（包括 identity 缺字段）→ **不返回**，默认拒绝；
- 未声明限制 → 共享工具，所有身份可见；
- 请求 `scope` 时，工具必须声明同 scope 或带同名 tag（沿用旧语义）。

装配期校验：`ToolRegistry.register` 校验工具名、JSON Schema、字段类型；
`ToolActionPort.validate()` 校验目录；`PortSet.check()` 调用它。工具注册本身
不进入 内核。

## 4. 审批恢复

### 4.1 调用形态

```python
first = await ports.action.call(identity, "deploy", {"env": "prod"})

if first.status == "needs_approval":
    # 1) 落审批单（内存或 SQLite 队列）
    ticket = ports.action.request_approval(identity, first)

    # 2) 暂停：把当前状态存检查点，等待外部审批系统
    ports.state.checkpoint("thread-1", "await_approval", {"ticket_id": ticket.id})

    # 3) 人工/外部系统给出决定后恢复；decision 也可以是 bool 或 dict
    done = await ports.action.resume(ticket.id, "approve")
```

### 4.2 字段与状态

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `ActionResult`（首次 `call`） | `ok=False`、`status="needs_approval"`、`approval_id`、`meta.tool/args/ctx`、`error` | 由注册表返回 `{"needs_approval": True, ...}` 时映射出来 |
| `ApprovalTicket` | `id`、`tenant_id`、`actor`、`tool`、`payload={"args","ctx"}`、`status`、`reason`、`created_at`、`decided_at`、`decided_by` | `request_approval` 会复用 `ActionResult.approval_id` 作为 `ticket.id`；正常路径下两者相等 |
| `resume` 返回 | `ActionResult` | 批准则重新调用工具；拒绝返回 `ok=False, status="denied"`；审批单不存在也返回 `denied`，不抛异常 |

`decision` 的可接受形式：

| 形式 | 示例 | 结果 |
|---|---|---|
| 字符串（批准） | `"approve"` / `"approved"` / `"allow"` / `"ok"` / `"yes"` / `"true"` / `"通过"` / `"同意"` | 批准 |
| 字符串（拒绝） | `"reject"` / `"rejected"` / `"deny"` / `"denied"` / `"no"` / `"false"` / `"拒绝"` / `"驳回"` | 拒绝 |
| 布尔 | `True` / `False` | 批准 / 拒绝 |
| 字典 | `{"decision": "approve", "by": "alice", "reason": "..."}` | 同时记录裁决人和原因 |
| 其他字符串 | `"maybe"` | 按拒绝处理，原因写“未知审批结论” |

### 4.3 `approved_override` 的作用

| 问题 | 答案 |
|---|---|
| 谁写入 | `ToolActionPort.resume()` 在批准后把 `ctx["approved_override"] = True` 写回调用上下文 |
| 谁读取 | `ToolRegistry.execute()` 检测到该标志后，跳过外部 `policy.check` 整段判定（不再产生 `deny` 或 `ask`） |
| 跳过的范围 | 只跳过注册表的工具策略判定；白名单、`before_tool` hooks、参数校验、业务扩展检查仍照常执行 |
| 不是什么 | 不是全局开关，也不会写入审批单以外的持久状态；只在这次重新调用中生效 |

### 4.4 已知行为（宿主需自行兜底）

| 行为 | 说明 |
|---|---|
| 重复 `resume` 幂等 | 同一审批单第二次 `resume` 返回 `ok=False, status="error"`（“审批单已处理”），不会重复执行工具。宿主仍应把重复回调识别为无操作 |
| 队列选择 | 默认 `InMemoryApprovalQueue` 只适合单进程；服务重启或多副本必须用 `SQLiteApprovalQueue` 或外部审批系统 |
| 身份来源 | `resume` 重新调用时只用审批单里的 `tenant_id` / `actor` 和 `payload.ctx`，不会重新调用 `IdentityPort.resolve` |
| 审计 | 批准/拒绝都会写一条 `approval:<tool>` 审计；重新调用工具还会再写一条 `tool:<name>` 审计 |
| 同一 run 继续 | `RunHandle.resume()` 会沿用原 `run_id` / `trace_id` 并从挂起状态（消息、用量、账本）接着跑；审计和检查点因此保持连续，不再新开 run |
| 动作端口审批 | `action_mode="port"` 时 `needs_approval` 由 `ActionPort` 返回，运行进入 `blocked`；恢复仍由宿主调 `action_port.resume()`，结果不自动回灌当前 run |

## 5. 状态与 LangGraph

### 5.1 状态端口：`SQLiteStatePort` / `PostgresStatePort`

两者方法契约完全一致，只是落库位置不同：SQLite 用 `run_state` + `run_checkpoint`
两张表；PostgreSQL 用 `harness_run_state` + `harness_run_checkpoint`，`state` 为 JSONB。
下表以 SQLite 为例，PostgreSQL 行为相同。

| 方法 | 行为 |
|---|---|
| `load(thread_id)` | 读 `run_state` 表；不存在返回 `None` |
| `save(thread_id, state)` | 按 `thread_id` upsert，并更新 `updated_at` |
| `checkpoint(thread_id, node, state=None)` | 写入 `run_checkpoint`，`parent_id` 指向该线程最近一条检查点；`state` 省略时取 `load()`；返回新检查点 id |
| `resume(thread_id)` | 返回最近一条检查点的 `state`；没有检查点时回退到 `load()` |
| `list_checkpoints(thread_id)` | 按创建顺序返回检查点元数据，**不含 `state` 正文** |
| `prune(before=None, retention_days=30)` | 可选能力（不在协议内）：删除 cutoff 之前的状态与检查点，返回删除行数 |

存储落地：`run_state`（每线程一行当前状态）+ `run_checkpoint`（追加式检查点链），只用标准库 `sqlite3`，**不 import langgraph**，因此只有基础依赖时也能启动。需要多副本时换 `PostgresStatePort`，契约不变。

### 5.2 与 LangGraph 的关系

| 维度 | 默认 `SQLiteStatePort` | 宿主替换为 LangGraph checkpointer |
|---|---|---|
| 依赖 | 仅标准库 | LangGraph 及其 checkpointer |
| 定位 | 单机/低配默认门面，保证基础依赖可跑 | 已有 LangGraph 图执行时可复用其断点能力 |
| 接入方式 | 直接实例化传路径 | 写一个适配器实现同样的 5 个方法，再传给 `PortSet(state=...)` |
| 权威来源 | 只能是其中一个 | 不要让 SQLite 与 checkpointer 同时当权威；选一个，另一个只做导出 |
| `thread_id` | 直接作主键 | 映射到 checkpointer 的 `thread_id` / config 键 |

适配器骨架（方法签名必须与 `StatePort` 一致）：

```python
class LangGraphStatePort:
    """宿主实现：把 LangGraph checkpointer 包成 StatePort。"""

    def __init__(self, checkpointer):
        self.checkpointer = checkpointer

    def load(self, thread_id: str) -> dict | None:
        ...

    def save(self, thread_id: str, state: dict) -> None:
        ...

    def checkpoint(self, thread_id: str, node: str,
                   state: dict | None = None) -> str:
        ...

    def resume(self, thread_id: str) -> dict | None:
        ...

    def list_checkpoints(self, thread_id: str) -> list[dict]:
        ...
```

注意：不同 LangGraph 版本的 checkpointer 内部 API 不同，适配器内部如何映射由宿主按其版本完成；本文不声称存在现成适配器。

## 6. 审计合规

### 6.1 实现要点

| 项目 | 当前实现 |
|---|---|
| 写入 | `SQLiteAuditPort.emit(event)` / `PostgresAuditPort.emit(event)`；接受 `AuditEvent` 或同名字段字典，返回落库后的 `AuditEvent` |
| 只追加 | API 层只提供 `emit` / `query` / `verify_chain` / `prune`，没有 `update` |
| 哈希链 | 每条记录计算 `prev_hash` 与 `hash`，按 `(at, rowid)` 顺序串成链 |
| 哈希算法 | `sha256(canonical)`；`canonical` 是对参与字段做 `sort_keys=True` 的 JSON |
| 参与哈希的字段 | `id / tenant_id / actor / action / target / decision / reason / trace_id / at / prev_hash`（不含 `hash` 自身） |
| 查询 | `query(filter)` 支持 `tenant_id / actor / action / decision / trace_id / since / until / limit`，也可传回调函数 |
| 默认留存 | `retention_days=180` |
| 清理 | 必须显式调用 `prune(before=None)`；不传 `before` 时按 `now - retention_days * 86400` 计算截止时间，返回删除行数 |
| 自动清理 | 没有后台定时任务；不调用 `prune` 就不会删除 |

### 6.2 `verify_chain()`

```python
report = audit.verify_chain()
# {"ok": True, "checked": 3, "broken_at": ""}
```

| 返回字段 | 含义 |
|---|---|
| `ok` | 整条链是否通过 |
| `checked` | 校验通过的记录数；断链时是断点之前的数量 |
| `broken_at` | 第一条不匹配记录的 id；全部通过时为空串 |

校验会重算每条记录的 `prev_hash` 与 `hash`；修改任意历史字段（即使只改 `decision`）都会返回 `ok=False`。

### 6.3 留存与清理的注意点

| 注意点 | 说明 |
|---|---|
| 部分清理会破坏链校验 | `prune` 是物理删除。删掉早期记录后，首条幸存记录的 `prev_hash` 仍指向已删除记录，`verify_chain()` 会报 `ok=False`（已用代码验证）。需要保留可验证链时，应先导出/归档，或整段清理后接受“从当前基线重新开始”的合规口径 |
| 审计失败不阻断主链路 | `ToolActionPort._audit` 捕获所有异常并忽略；审计库写失败不会让工具调用失败，但会静默丢失证据。宿主必须另行监控 `verify_chain()` 与审计写入量 |
| 生产存储 | `SQLiteAuditPort` 是默认实现；多副本可用 `PostgresAuditPort`（固定 advisory lock 串行哈希链），更高合规要求再接产品审计库或 SIEM；本文不声称已提供外部审计适配器 |

## 8. 常见错误

| # | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 1 | `isinstance(obj, IdentityPort)` 为 `True`，运行期却报参数错误 | `runtime_checkable` 只检查方法名是否存在，不检查签名。例如 `def resolve(self):` 少 `req` 参数仍会被判为 `IdentityPort` | 除 `PortSet.check()` 外，启动时做一次真实调用冒烟测试；用类型检查/契约测试兜住签名 |
| 2 | 把 `SQLiteMemoryStore(...)` 直接传给 `PortSet(memory=...)` | `MemoryPort.query(req)` 收一个请求 dict；`SQLiteMemoryStore.query(tenant_id=..., scope=...)` 收列参数，两者签名不兼容 | 必须用 `StoreMemoryPort(store)` 适配；查询时传 `{"tenant_id": ..., "scope": ..., "scope_id": ..., "agent_id": ...}` |
| 3 | 记忆查询跨智能体串数据 | `StoreMemoryPort` 只有在请求 dict 里出现 `agent_id` 时才把它下推给存储；不传就按租户+范围查全部智能体 | 按智能体隔离的场景必须显式传 `agent_id` |
| 4 | `PortSet.check()` 报 `knowledge` 不完整 | 只实现了 `search`，漏了 `get_chunk` | `KnowledgePort` 必须同时实现 `search` 与 `get_chunk`；检索命中无 `source` 时调用方要丢弃 |
| 5 | `PortSet()` 明明有默认实现却启动失败 | `PortSet` 不会自动填充默认实现，10 个字段默认都是 `None` | 显式实例化每个默认实现并传入 |
| 6 | `coroutine was never awaited` / 工具没有执行 | `ActionPort.call` 与 `resume` 是 `async` 方法 | 使用 `await`；同步上下文用 `asyncio.run(...)` |
| 7 | `list_tools` 报参数不匹配 | 自定义注册表的 `list_tools` 要求 `identity`，但 `ToolActionPort` 调用的是无参 `registry.list_tools()` | 注册表适配 `ToolRegistry` 形态，或在外面包一层 |
| 8 | 以为装了 `AccessPolicyPort` 就限制了工具调用 | `AccessPolicyPort` 在 `assemble` 中判块读取；工具调用的 allow/ask/deny 由 `ToolRegistry` 自己的 `policy` 决定 | 两处分别注入：`PortSet(policy=...)` 与 `ToolRegistry(policy=...)` |
| 9 | `extra_blocks` 抛 `TypeError: 不支持的块类型` | `assemble` 只接受 `Block` / `BlockMeta`，不接受 `MemoryRecord` | 先把记忆记录转成 `Block(BlockMeta(...), record.content)` 再传入 |
| 10 | 验收总是失败，或“请手动执行”被判失败 | `RuleVerifyPort` 默认 `forbid_handoff=True`，命中转交话术即失败；空结果也失败 | 按任务传 `criteria`；确需允许转交时显式设 `forbid_handoff=False` |
| 11 | 审计表里有记录，但 `verify_chain()` 报断链 | 曾经部分 `prune`，首条幸存记录的 `prev_hash` 指向已删除记录 | 清理前导出归档；或整段清理并明确新的合规基线；定期跑 `verify_chain()` |
| 12 | 同一个审批单恢复两次，工具执行两次 | `resume` 不校验审批单是否已裁决 | 宿主在审批层加幂等键/一次性消费；不要把重复回调直接转给 `resume` |
| 13 | 重启后 pending 审批丢失 | 使用了默认 `InMemoryApprovalQueue` | 多副本/需重启恢复时改用 `SQLiteApprovalQueue(path)` 或外部审批系统 |
| 14 | `state.resume(thread_id)` 拿到的是旧状态 | 有检查点时优先返回最近检查点，不是 `run_state` 的最新 `save` | 明确区分“当前状态”与“最后检查点”；需要当前状态时用 `load()` |
| 15 | `ModuleNotFoundError: psycopg` | 没装 PostgreSQL 可选依赖 | `pip install 'enter-harness[postgres]'` |
| 16 | `缺少 PostgreSQL DSN` | 参数与 `HARNESS_PG_DSN` / `DATABASE_URL` / `PG*` 都没提供 | 传 `dsn=` 或设 `HARNESS_PG_DSN` |
| 17 | PG 建表时报 `permission denied for schema public` | 账号无 CREATE 权限（PG 15+ 默认收回） | `GRANT USAGE, CREATE ON SCHEMA public TO <user>;`，或由 DBA 预建 `harness_*` 表 |
| 18 | 知识端口搜不到任何内容 | 只入库未 `approve`、无 `source`，或查询没带 `tenant_id` | 检索只返回 `approved` 且有 `source` 的记录；多租户必须显式传 `tenant_id` |
| 19 | 从 SQLite 切到 PostgreSQL 后数据为空 | 三套后端之间没有自动迁移 | 先导出旧库再重放；不要假设切后端会复制数据 |
